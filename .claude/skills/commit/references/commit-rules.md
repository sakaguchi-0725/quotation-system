# コミットルール

このリポジトリでコミットを作成する際に従うルール集。

## 0. 言語

- 件名・本文は日本語で書く(type/scopeなどConventional Commitsのキーワードは英語のまま)

## 1. 件名・本文の書き方(Chris Beamsの7つのルール)

1. 件名と本文は空行1つで分ける(Gitツール群が件名を「タイトル」として扱う仕組みに依存するため)
2. 件名は50文字以内に収める(簡潔さの強制。長くなる場合は変更が atomic でない兆候)
3. 件名の先頭は大文字にする
4. 件名末尾にピリオドを打たない
5. 件名は命令形(imperative mood)で書く — 判定法: "If applied, this commit will [件名]" が文として成立するか。○ "Refactor subsystem X" / ✗ "Fixed bug with Y"
6. 本文は72文字で折り返す
7. 本文には「何を」ではなく「何を・なぜ」を書く。実装の詳細(How)はdiffを見れば分かるが、意図・背景・トレードオフは書かなければ消える

## 2. メッセージ形式(Conventional Commits)

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

- 必須type: `fix`(バグ修正)、`feat`(新機能)
- 推奨type(Angular準拠): `build`, `chore`, `ci`, `docs`, `style`, `refactor`, `perf`, `test`
- scope: `fix(parser):` のように対象範囲を名詞で括弧書きする(任意)
- 破壊的変更がある場合はフッターに `BREAKING CHANGE: 説明` を書く

## 3. コミットの粒度(Atomic Commits)

- 1コミット = 1つの論理的変更単位。かつ各コミット時点でリポジトリが動作する状態を保つ
- リトマス試験: 「このコミットは何をした?」を "and" を使わず1文で説明できるか
- フォーマット変更とロジック変更を同一コミットに混ぜない
- diffに複数の論理的変更単位が混在している場合は、コミットを分割することを提案する
- 理由: `git bisect` の精度、revert/cherry-pickのしやすさ、レビューのしやすさに直結する

## 適用時のチェックリスト

コミットを作成する前に以下を確認する。

- [ ] 件名・本文は日本語で書かれているか
- [ ] diffの中身が1つの論理的変更単位になっているか(混在していれば分割を提案)
- [ ] typeは変更内容と一致しているか(`feat`/`fix`/`docs`/`refactor`/`chore`など)
- [ ] 件名は50文字以内・命令形・大文字始まり・ピリオドなし
- [ ] 本文が必要な変更(背景説明が要るもの)か判断し、必要なら「なぜ」を書く
- [ ] 本文は72文字で折り返す
- [ ] 破壊的変更があれば `BREAKING CHANGE:` フッターを付ける
